# Принцип полного системного аудита

Этот проект нельзя улучшать серией несвязанных исправлений по одному сообщению об ошибке. Любое изменение поведения Worker/JARVIS проходит один и тот же проверяемый цикл.

## Обязательная карта пути

Перед изменением нужно проследить реальный путь задачи:

`goal -> observation -> UI state -> planning -> grounding -> policy -> execution -> validation -> experience -> skill/principle -> teacher -> self-improvement`

Для каждой стадии фиксируются:

- входные и выходные данные;
- владелец состояния;
- используемая модель или детерминированный код;
- условия успеха и остановки;
- повторные вызовы и таймауты;
- журналируемые доказательства;
- модульные и сквозные тесты.

## Правило исследования

1. Индексировать весь репозиторий, а не только найденный фрагмент.
2. Читать вызывающие и вызываемые модули, конфигурацию, PowerShell-мосты, frontend и тесты.
3. Сравнивать стадии с официальной документацией и исходными репозиториями актуальных GUI-agent систем.
4. Не переносить чужую архитектуру вслепую: сначала сформулировать конкретный разрыв и измеримый ожидаемый эффект.
5. Сначала создать воспроизводящий тест, затем минимальный patch.
6. Проверить модульный этап, контракт между этапами и полный цикл.

## Definition of done

Изменение завершено, только если:

- первопричина доказана;
- тест падал до исправления и проходит после него;
- полный набор тестов не имеет регрессий;
- состояние и ошибки наблюдаемы в журнале;
- живой UI-тест выполнен либо честно помечен как непроверенный;
- пользователь получил список изменённых файлов, результаты тестов и остаточные ограничения.

Исчезновение текста ошибки без доказанного достижения пользовательского результата не считается исправлением.
